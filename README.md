**包含30個維護作業、3個電子簽核流程。

## 專案概述

TigerInCodex 以文具製造暨批發業務為實作案例，由 Codex 分階段建立真實可操作的網頁、API 與 SQLite 資料庫。

主要流程涵蓋：

`原料採購 → 採購入庫 → BOM／製程 → 製造工單 → 生產領退料 → 完工回報 → 成品入庫 → 銷售出貨`。

系統也支援客戶與供應商退貨、整倉盤點、庫存調整、跨倉調撥、即時庫存查詢、庫存異動與製造批號雙向追溯，以及採購／製造／銷售統計。這些功能與普通 CRUD 不同，涉及已提交單據、真實庫存分錄及跨模組來源資料的一致性。

### 驗收里程碑

| 項目 | 結果 | 驗證範圍 |
|---|---|---|
| 原始 30 個 ERP 業務作業 | **User 功能驗收 30／30 PASS** | 2026-11-21 完成的本機功能驗收，依當時實際畫面及 User 回覆 |
| 採購單電子簽核 | **已實測部分 PASS** | 採購單直接送簽、四關簽核、第三關兩人會簽、退回重簽、本人撤銷及不可覆寫歷程 |
| Windows 獨立系統匯出 | **Codex 實作及隔離測試 PASS** | 已產生包含當時業務資料的自帶執行環境 ZIP；未收到獨立的 User 最終驗收 PASS |
| SQLite 備份／清空／恢復 | **Codex 隔離測試 PASS** | 實際 User 資料庫僅執行非破壞性備份；未對 User 正式資料執行清空或恢復驗收 |

**注意：**「30／30 PASS」僅指原始 30 個業務作業的 User 功能驗收，不等於電子簽核全部功能、獨立 EXE、資料庫維護、企業權限、資安或公開上線皆已驗收通過。

## 技術架構

| 層次 | 採用技術 | 用途 |
|---|---|---|
| 前端 | React、TypeScript、Vite、Tailwind CSS | 繁體中文 ERP 導覽、表單、主從明細、查詢及簽核介面 |
| 後端 | Python、FastAPI | 業務 API、來源驗證、計算與交易操作 |
| 資料存取／遷移 | SQLAlchemy、Alembic | 資料模型、資料庫交易及結構版本管理 |
| 資料庫 | SQLite | 本機業務資料、稽核及交易紀錄 |
| 自動驗證 | pytest、Playwright | 後端與桌面瀏覽器測試；不取代 User 親自驗收 |

數量、金額與 SUM 的設計重視**精確十進位運算**；庫存以正式過帳的來源與分錄為依據，而不是讓使用者任意改寫品項主檔上的「現存量」。已過帳的歷史與關聯來源也必須保留。

## Windows 本機啟動

以下適用於**已完成專案環境與相依套件安裝**的開發工作區，並非全新電腦的一鍵安裝指令。

在 ERP 專案根目錄執行：

```powershell
.\.venv\Scripts\python.exe scripts\dev.py
```

啟動後開啟：

- ERP 網頁：<http://127.0.0.1:5173/>
- FastAPI 文件：<http://127.0.0.1:8000/docs>
- 電子簽核待辦：<http://127.0.0.1:5173/#approval-inbox>

開發版的前後端分別使用本機連接埠 `5173`、`8000`。服務應只監聽 `127.0.0.1`，**不要暴露至公網、區網或建立 tunnel**。埠若被占用，應先查明是否為同一專案尚未退出的舊服務，不要任意結束不相關程序。

### 資料保存

- 開發版的既有業務資料庫為 `data/erp.sqlite`。
- 瀏覽器 `F5` 是重新讀取介面，**不是清空或重建資料庫**。
- 真實入庫、出庫、退貨、調整、調撥及簽核操作可能寫入持久化資料；不要直接在 User 的正式展示資料庫執行自動測試。
- 測試應使用**隔離資料庫**；修正程式前先保存可復原的備份。

## 六大模組與 30 個作業

### A. 基本資料管理（01–08）

| 編號 | 作業 |
|---|---|
| 01 | 商品分類維護 |
| 02 | 原物料資料維護 |
| 03 | 成品資料維護 |
| 04 | 客戶資料維護 |
| 05 | 供應商資料維護 |
| 06 | 倉庫資料維護 |
| 07 | 工作中心維護 |
| 08 | 供應商供料設定 |

原料與成品可共用同一品項身分，但以不同維護入口操作；供應商與原料可以透過供料設定建立多對多配對，並記錄供應商供貨價格。

### B. 採購管理（09–12）

| 編號 | 作業 |
|---|---|
| 09 | 採購訂單管理（表頭、明細、SUM） |
| 10 | 採購入庫管理 |
| 11 | 供應商退貨管理 |
| 12 | 未到貨採購查詢 |

採購單明細金額合計為採購總金額；真正驗收入庫才增加庫存，正式退貨才扣除庫存。未到貨查詢區分原訂購、已收貨與仍未到貨數量。

### C. 製造生產管理（13–20）

| 編號 | 作業 |
|---|---|
| 13 | 產品 BOM 用料表 |
| 14 | 製程設定 |
| 15 | 製造工單管理 |
| 16 | 智慧物料需求與缺料分析（MRP Lite） |
| 17 | 生產領料管理 |
| 18 | 生產退料管理 |
| 19 | 生產完工回報 |
| 20 | 成品入庫管理 |

BOM 表示成品與所需原料及標準用量；MRP Lite 可合併多張工單的需求。生產領料／退料產生實際原料出入庫；完工回報記錄良品與不良品，**本身不等於成品入庫**。

### D. 銷售管理（21–24）

| 編號 | 作業 |
|---|---|
| 21 | 銷售訂單管理（表頭、明細、SUM） |
| 22 | 銷售出貨管理 |
| 23 | 客戶退貨管理 |
| 24 | 未出貨訂單查詢 |

正式銷售出貨會扣除成品庫存；經確認可回庫的客戶退貨以獨立正向分錄增加庫存，保留原出貨歷史。未出貨量按原訂購量與累計**毛出貨量**計算，不將客戶退貨直接誤算成未出貨。

### E. 庫存管理（25–27）

| 編號 | 作業 |
|---|---|
| 25 | 庫存盤點管理 |
| 26 | 庫存調整管理 |
| 27 | 倉庫調撥管理 |

整倉盤點包含凍結、帳面快照、實盤與結案；正式庫存調整建立帶正負號的分錄；跨倉調撥在來源倉扣庫、目的倉入庫，公司同品項總量保持不變。

### F. 查詢與報表（28–30）

| 編號 | 作業 |
|---|---|
| 28 | 原料與成品即時庫存查詢 |
| 29 | 庫存異動與製造批號雙向追溯 |
| 30 | 採購、製造、銷售統計 |

查詢可呈現公司合計與不同倉庫／批號存量，並依實際保存的來源關聯正向或反向追溯。**共同工單或共同批號的關聯，不代表已掌握每一單位原料的精確耗用分攤**；無證據時不能捏造來源。

## 電子簽核：已實測的採購單流程

電子簽核是原始 30 作業之外的擴充；本節**只記錄有 User 實際測試證據的採購簽核功能**。

### 操作方式

1. 在 ERP 上方選取**目前部門**與**目前員工**，以模擬指定簽核人員。這是展示模式，**沒有驗證登入身分**。
2. 開啟已儲存的採購單，在原採購單操作區使用 **「送出簽核」**。
3. 切換至應處理的示範員工，從 **「待我簽核」** 開啟申請，檢視送簽時凍結的單據內容、進度及歷程。
4. 在真正輪到的關卡執行適用操作；切換員工後，待辦數量與可用動作依當前簽核狀態呈現。

### 採購單四關流程

```text
第 1 關  申請部門主管
           ↓ 同意
第 2 關  採購主管
           ↓ 同意
第 3 關  財務主管 ＋ 倉庫主管（兩位皆須同意）
           ↓ 兩人完成後才放行
第 4 關  總經理
           ↓ 同意
         簽核完成
```

**User 已驗收的採購簽核行為：**

- 採購單可直接送簽並依序完成四關；第三關須由財務與倉庫兩位主管皆同意，才會進入第四關。重新整理、申請人回看與原採購金額保存均經 User 確認。
- 已測試退回上一關、重新同意及撤銷本人簽核；每次重開審查保留原事件，沒有覆寫既有歷程。

個別測試單號、金額與驗收截圖保留於私人紀錄，不公開於本儲存庫。

簽核紀錄屬於本機示範操作與業務歷程驗證，**不代表已完成身分認證、法律有效的數位簽章或不可否認性驗證**。本次 README 不宣稱其他未經 User 實際測試的簽核情境已 PASS。

## SQLite 備份、清空與恢復

ERP 上方提供三個獨立控制：**「備份 SQLite」／「清空 SQLite」／「恢復 SQLite」**。

- **備份 SQLite：** 透過 SQLite 一致性快照保留當時已提交的業務資料。開發版備份位置位於資料庫相應的 `backups/sqlite` 目錄。
- **清空 SQLite：** 只有在後端確認有**成功且仍有效的備份**時，才可進入清空流程；操作還需確認並輸入指定文字 `清空`。清空會刪除業務紀錄，**不是一般測試用的重新整理功能**。
- **恢復 SQLite：** 由既有備份恢復資料；執行前另保留保護性副本，以利事故追查或回復。

這些為 Codex 在隔離資料庫／隔離執行檔中回報已驗證的功能。**不要為測試目的對真實 User `data/erp.sqlite` 執行清空或恢復。** 開發版資料庫的實際寫入狀態可能改變備份有效性，不能只因畫面曾經顯示可清空，就假設現在仍安全。

## 匯出獨立 Windows ERP

網頁上方的 **「匯出獨立系統」** 用於產生可在 Windows 上獨立啟動的 ERP ZIP。已完成的 Codex 交付曾包含：

- `TIGER-ERP-Standalone.zip` 與 `TIGER-ERP.exe`；目標電腦不需要另外安裝 Python、Node.js 或 Vite。
- **匯出當下的一致性 SQLite 資料快照**，包括當時已提交的 User 業務資料，而非自動改為空白資料庫。
- 第一次啟動時從不可變的種子資料庫建立獨立的可寫資料庫；往後重啟沿用自身資料，與開發版原資料庫**不自動同步**。
- 以本機 `127.0.0.1` 開啟獨立執行環境。

## 驗證、資料保護與使用限制

- **User 功能驗收：** 原始 30 個 ERP 作業已於 2026-11-21 獲 `30／30 PASS`；採購電子簽核另以兩張測試單確認本 README 所述的操作。其他功能不得依此推定全部已驗收。
- **Codex 自動驗證：** pytest、Playwright、建置與隔離資料庫檢查是開發證據；與 User 本人操作的證據層級不同。本 README 不聲稱 ChatGPT 直接執行了本機程式或 SQLite 查核。
- **既有資料保護：** 不得以測試覆蓋、清空或重建 User 業務資料。單據歷程、庫存分錄、來源關聯及備份不應為了重新驗收而重置。
- **企業決策：** D01–D16 仍有待核准政策；不能將安全的本機展示操作自動視作企業全部業務政策獲核准。
- **資安狀態：** `SECURITY: PARTIAL — RISK CONTAINED`。已知依賴安全問題未被宣稱完成修補；本機功能 PASS **不等於** `SECURITY CLEARED`。
